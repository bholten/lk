  Comprehensive Review of lk

  1. Design Doc Incongruences

  Event routing order differs from spec. The design docs (design_draft.md, brainstorming.md) specify DOM-style capture → target →
  bubble for all event handling. The actual implementation in lk-event.c:297-401 does something different: widget vtable dispatch
  runs first (target → bubble), and then the user event handler runs capture → target → bubble. This means widget handlers never
  see capture phase, and the user handler runs after widgets have potentially consumed the event. The documented model suggests a
  single unified capture → target → bubble pipeline where widgets and user handlers interleave in the same phases.

  Hover state is declared but never populated. LK_NSTATE_HOVERED is defined in lk.h:663 and the style resolver properly matches
  against state masks, but lk-sdl.c never computes or sets hover state anywhere. The node_states array used by lk_style_resolve is
   never populated with LK_NSTATE_HOVERED. Any theme rules matching hovered state will silently never fire.

  Style resolution order differs from styles.md spec. The doc defines resolution as: (1) rules, (2) kind defaults, (3) tree prop
  overrides, (4) inheritance. The implementation in lk-style.c:199-317 combines steps 1 and 2 (kind defaults are just rules in the
   default theme) — which is fine — but applies tree prop overrides before inheritance. The doc says tree props "unconditionally
  win" and suggests they override everything, but inheritance currently only fills in unset fields. Since tree prop overrides mark
   fields as set via set_mask, they properly prevent inheritance. This ordering is actually correct despite looking different from
   the doc's numbered steps.

  lk_ht is declared public but unimplemented. lk.h:804-822 declares a complete hash table API (lk_ht_get, lk_ht_set, lk_ht_length,
   lk_hti_iterator, lk_hti_next) but lk-ht.c only implements new and delete — everything else is a TODO comment. This is dead
  public API surface. It should either be removed from the header or implemented.

  Schema validation is stubbed. lk_tree_validate_schema is declared and called, but returns immediately. The design docs mention
  per-kind prop validation. Not necessarily a bug, but it's a promise that hasn't been honored.

  lk_style_trace doesn't free its own memory. The lk_style_trace struct allocates via lk_sys_alloc but there's no
  lk_style_trace_destroy or similar function. Callers must know to lk_sys_dealloc the entries pointer themselves.

  2. Allocator Discipline Issues

  lk-ht.c uses raw malloc/calloc/free. This directly violates the stated convention: "never call malloc/free directly in core
  code; use lk_alloc/lk_dealloc or the struct's own allocator pointers." Lines 25, 34, 37, 47-52.

  lk-style.c uses lk_sys_alloc directly (the system default allocator) rather than threading a custom allocator through lk_theme.
  Every other major struct (lk_tree, lk_ui, lk_intern) supports custom allocators. The theme is the exception.

  lcl-lk.c uses raw malloc/free at lines 721, 870, 1595, 1668 for the command handler context and window wrapper. While the
  bindings are arguably not "core code," this inconsistency could bite you if you ever want to track allocations or embed in a
  restricted environment.

  3. Allocation in Hot Paths

  Per-node temp allocations in DFS traversals. Several functions allocate a temporary kids array for every node with children
  during traversal, just to reverse child order for correct DFS:

  - lk-event.c:62,174 (hit test + focus collection)
  - lk-style.c:300 (style resolution)

  This is O(n) allocations per frame for n parent nodes. A simpler approach: push children directly to the stack in forward order
  and accept reverse-DFS, or use a single pre-allocated scratch buffer sized to max-children.

  4. Code Smells and Maintenance Concerns

  Fixed-size path buffer in event routing. lk-event.c:299 uses lk_ix path[64] — a hard-coded max tree depth. The check at line 317
   silently truncates the path if the tree exceeds depth 64. For a toolkit that may host text editors (Weft), deeply nested
  structures aren't impossible. A dynamic allocation or at least a diagnostic warning would be safer.

  Text cache is fixed at 256 slots with no eviction. lk-sdl.c uses a 256-slot open-addressing text texture cache. When full, it
  falls back to re-rendering text every frame with no warning. For any non-trivial UI, this cache will saturate. An eviction
  policy (even a simple "destroy oldest on collision") would prevent performance cliffs.

  Scroll bar colors are hard-coded. In lk-scroll.c:183-199, the scroll bar track and thumb colors are magic constants rather than
  reading from the resolved lk_style. This breaks the principle that themes control appearance.

  lk_ht_new allocates the wrong size. lk-ht.c:25: malloc(elem_size) uses the caller's elem_size param to allocate the lk_ht struct
   itself. This should be sizeof(lk_ht), not elem_size. If elem_size < sizeof(lk_ht), this is a buffer overflow. The elem_size
  parameter isn't even stored or used afterward — it's vestigial.

  Double-free risk in Lcl UI finalizer. lcl-lk.c:179-189 acknowledges that after explicit lk_ui_destroy, the opaque finalizer will
   fire on an invalid pointer. The comment says "accept the finalizer will be called on a now-invalid pointer." This is a real
  use-after-free risk. A guard flag or nulling the opaque's internal pointer would fix it.

  6. Minor Issues

  - No .gitignore — build/, __pycache__/, etc. are untracked but not ignored.
  - docs/ directory appears untracked in git — design docs should be committed.
  - lk_ht_delete frees all entry keys unconditionally (lk-ht.c:48) even though nothing in the current code ever sets keys (since
  lk_ht_set isn't implemented). If someone implements set with non-heap keys, this will crash.
  - lk_ht_new with elem_size <= 0 check uses size_t which is unsigned — <= 0 is equivalent to == 0 and the < 0 branch is dead
  code.

  7. What's in Good Shape

  The core architecture is solid. Specific strengths:

  - C89 compliance is excellent across all core files. No violations found.
  - Arena-backed tree with interned strings works well. The diff algorithm is correct.
  - Widget vtable system is clean and extensible. The scroll widget is a good proof of the pattern.
  - Style resolver correctly implements rule matching, partial styles, inheritance, and tree prop overrides. The lk_style_trace
  debugging API matches what the docs promised.
  - Text input widget is well-implemented with proper bounds checking and state management.
  - Lcl bindings are comprehensive (29 procs covering the full non-SDL API surface) with good test coverage (30 tests).
  - Presentation/command/translator pipeline is correctly implemented per the CLIM-inspired design.
